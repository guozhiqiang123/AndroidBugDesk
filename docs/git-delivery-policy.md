# AndroidBugDesk 合并与推送约定

本项目在独立任务分支中开发，在版本集成分支中汇总和验证，通过本版本验收后用 PR 合入 `master`。协调员按以下门槛推进正常推送、候选构建和 PR 合并，不需要使用者反复提醒。任务状态变化本身不执行 Git 合并。

生效日期：2026-10-09。远程仓库：[guozhiqiang123/AndroidBugDesk](https://github.com/guozhiqiang123/AndroidBugDesk)，公开仓库。本地仓库保留现有 `master` 名称和 Multica 任务分支。

## 分支职责

| 分支 | 用途 | 写入责任 |
| --- | --- | --- |
| `agent/...` | Multica 分配的任务或对话分支，保存独立模块成果 | 对应任务执行者 |
| 集成任务实际分配的 `agent/...` 分支 | 合并已接受成果、维护共享文件和执行集成验证 | 单一集成者 |
| `delivery/<版本号>` | 远程候选版本，指向集成任务已验证的提交，例如 `delivery/v0.1.0` | 单一集成者 |
| `master` | 已通过本版本约定验收的稳定代码 | 通过 GitHub PR 合并 |

集成者沿用 Multica 分配的 worktree 和任务分支，把候选提交推送到对应的远程 `delivery/<版本号>`。不为了遵循分支命名而切换或重置正在运行的任务分支。一个版本只有一名集成者更新候选分支。

## 什么时候推送

| 时机 | 允许的操作 | 必须满足的条件 |
| --- | --- | --- |
| 首次建立远程基线 | 将核对过的本地 `master` 首次推送为远程 `master`，随后启用保护 | 公开内容范围已确认、全部待推历史检查通过；只含研发基线和流程文档，不带未接受任务成果。此操作不表示首版整体验收通过 |
| 一个开发任务完成可检查的提交 | 正常推送该任务的明确分支 | 相关本地检查通过，文件所有权明确，记录提交与检查结果，待推提交和新增历史适合公开 |
| 并行成果已审查并完成集成 | 推送或正常快进更新 `delivery/<版本号>`，创建或更新版本 PR | 已接受的模块提交全部合入，集成检查通过，PR 标题或正文包含 Multica 父任务编号 |
| 候选提交完成独立技术验证 | 对该候选分支执行 Actions 安装包构建 | 精确提交固定，本版本目标平台明确，记录 Actions run、提交、产物及 SHA256 |
| PR 满足合并门槛 | 通过 GitHub 合并 PR，由 GitHub 更新远程 `master` | 下面的主分支合并条件全部成立 |

开发任务完成不需要等待整个父任务结束才备份到远程。候选分支必须在最终验收前推送，才能由 Actions 打包供安装验收。`Validate` 工作流会检查 PR 和 `master` 推送；当前任务分支单独推送不一定触发检查，以实际 workflow 为准。

第一次源码推送仍需要确认历史中的真实业务配置是否可以公开，或先完成脱敏和基线交接。公开仓库创建成功、绑定 `origin`、规则落档都不能代替这个门槛。发现凭据、真实测试证据、设备或用户隐私时停止对应推送，修正待推历史；只删除当前文件不能消除旧提交中的内容。

## 什么时候集成模块成果

协调员核对任务交付的实际分支、提交和相关检查后接受技术成果。版本集成任务收集这些提交，解决共享契约、命令注册和锁文件冲突，运行本地与 mock 联合验证。未通过审查的提交留在原任务分支返修。

当前首版的集成任务是 GZQ-49。源码目录中的 `master` 不作为并行任务的共享工作目录。正常合并和必要的 cherry-pick 都在集成者的 worktree 内执行，记录选取范围和原始提交，避免遗漏或重复引入成果。

## 什么时候合入主分支

协调员只有在以下条件全部成立时，才安排主分支合并任务执行 PR 合并：

1. 本版本范围、目标平台和必需验收项已确定；所有必需实现与返修成果已接受，没有未解决的阻断问题。
2. 候选提交完成集成验证和独立审查。GitHub PR 的最新 head 对应这些证据，所需检查实际通过；PR 与最新 `master` 可合并。
3. 本版本所需的 Actions 平台矩阵实际成功，安装包可取得，提交、平台、产物哈希和回执可对应。
4. 本版本所需的真机、安装与业务功能人工验收有明确结果。真实云效写入继续需要使用者指定测试范围；mock 成功不代替真实验收。只有使用者明确调整范围后，某个验收项才能延期或排除。
5. 待推历史的公开内容检查通过，且 PR 包含变更、验证和未覆盖范围的说明。不得用任务 `done`、运行结束或必需任务被取消来代替上述证据。

条件齐全后，协调员安排构建与集成成员按本约定执行合并，不再单独请求重复的 Git 合并许可。协调员不代替成员执行 Git 交付，具体分工见 `docs/multica-collaboration.md`。人工验收结果仍由人提供。本约定不授权替人填写通过结果、真实云效写入或产品发布。

PR 默认使用 merge commit，保留集成和任务提交历史。合并前重新核对 PR head；不得使用 `--admin`、跳过检查或强推来绕过保护。候选代码或依赖变动后，重新验证受影响部分并重新生成候选包。若 `master` 前进，需要在集成分支处理后重新检查。

GitHub 合并后记录 PR URL、候选提交和最终 `master` 提交；核对合并前后代码树及 `master` 的检查。合并提交和候选提交的 SHA 不同，必须分别记录；若实际代码树变化，原安装包不能继续代表合并后的代码。

## 合并后的本地同步与完成条件

合并任务 fetch 远程结果。原目录仍在 `master`、工作区干净且可以快进时，快进同步本地 `master`；如果使用者正在其他分支、存在未提交修改或分支分叉，保留现场，记录同步等待条件。不强制切分支，不 reset、clean 或替使用者提交修改。

首版在人工验收后新增阶段 8 主分支 PR 合并与本地同步，阶段 9 汇总。常规版本模板和已规划的下一版本也在汇总前设置同样的合并任务。父任务完成前必须有合并回执；本地同步未完成时在报告中明确说明，不能把源码目录描述为已更新。

GitHub 对合并 PR 引发的 Multica 状态变更只视为外部事件。即使某个任务因此自动变为 `done`，协调员仍按验收证据核对父任务，不能跳过剩余人工门槛。

## 推送与发布边界

本约定允许在本仓库内按门槛正常推送任务分支、更新候选分支、创建 PR、执行候选 Actions 构建和合并已验收 PR。它不包括强推、删除远程成果、改变可见性、绕过保护或改写已有公开历史。

`v*` tag、GitHub Release、签名、公证和正式分发需要单独的发布指令。bundle workflow 的 `v*` tag 会触发四平台打包，并在全部成功及完整性校验通过后创建 GitHub Release，因此不能为了得到测试包而随意创建发布 tag。候选安装包使用手工触发的 Actions artifacts。

禁止 `git push --all`、`--mirror` 或一次性推送所有 tags。每次只推送已核对的明确分支，上传前检查整个新增提交范围。PAT、钥匙串数据、日志、截图、视频、数据库和证据 ZIP 不进入源码仓库；GitHub 构建也不使用测试人员的云效 PAT。

## 主分支保护

远程 `master` 建立后启用：通过 PR 合并、要求当前 `Validate` 的实际检查成功、要求分支与基线更新、禁止强推和删除，保护规则对管理员生效。

GitHub 的保护负责 PR 和检查限制，人工安装与业务验收由 Multica 的合并门槛负责。当前是个人账号管理项目，不设置无法由提交者自己完成的强制审批数量；独立审查仍须在 Multica 留下证据。CI 改名或拆分时，构建配置任务必须同时核对 GitHub required checks。

## 平台规则依据

- Multica 的 worktree 成果保留在任务分支中，需要明确执行 merge 或 cherry-pick：[项目资源](https://multica.ai/docs/zh/project-resources)。
- GitHub 的 PR 与检查要求由主分支保护控制：[受保护分支](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)。
