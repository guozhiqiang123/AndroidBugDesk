# 采集范围与存储优化

确认日期：2026-10-10。

## 问题与目标

审查确认原实现存在三类浪费：整机 `adb bugreport` 对所有问题类型默认启用；普通日志包含整机 main/system/crash/events，且 Crash 缓冲区会被崩溃专项再次采集；生成附件时保留中间源文件，重复采集只替换草稿引用而不删除旧受管文件。macOS 默认打开 ZIP 还会由 Archive Utility 解压到附件目录。

本轮目标是让默认采集只覆盖目标应用与问题类型所需信息，整机报告改为明确的人工兜底，并保证每个成功生成的附件在本地只有一个受管副本。

本机抽样中，单个整机报告约 14–17 MB；成功报告原先还会同时保留原始目录和附件副本。受管附件目录中也存在多组由中间文件和最终文件形成的相同哈希 ZIP。这说明体积问题主要来自整机报告、生成链路副本和重复采集，而非截图本身。

优化后再次对已连接 Pixel 4 XL 做只读体积抽样：内存摘要约 1.1 KB、磁盘余量约 195 B、CPU 汇总约 7.4 KB、完整进程表约 67 KB、完整网络统计约 180 KB。相较 14–17 MB 的系统报告，这些专项证据体积有限且能直接支持资源竞争与网络路径分析，因此保留，不以体积为由删除。

## 全部采集项审查

| 采集项           | 审查结论                                   | 调整                                         |
| ---------------- | ------------------------------------------ | -------------------------------------------- |
| 设备与应用环境   | 与网络等专项重复，旧输出可达 MB 级         | 保留屏幕、内存、磁盘等高价值摘要             |
| 现存日志         | 原为整机缓冲区，且包含 crash               | 按目标应用 UID 过滤，读取 main/system/events |
| 当前截图         | 内容独立，但生成时曾保留中间副本           | 保留，删除临时源文件                         |
| 当前界面层级     | 与截图互补，可定位控件结构                 | 保留，仅按问题类型选择                       |
| 应用与进程状态   | 已由包名限定                               | 保留                                         |
| 窗口与显示状态   | 包含系统上下文，但 UI、ANR 诊断需要        | 仅对应问题类型按需采集                       |
| 语言与字体配置   | 与通用环境有少量字段交集                   | 通用环境不进入补采默认组合，专项保留         |
| 崩溃日志         | 原与现存日志的 crash 缓冲区重复            | 拆为独立 UID 过滤项                          |
| 历史进程退出记录 | 目标包限定                                 | 保留                                         |
| 当前应用内存     | 目标包限定                                 | 保留                                         |
| 现存帧统计       | 目标包限定                                 | 保留                                         |
| CPU 与进程状态   | CPU 占用和完整进程关系共同用于判断系统竞争 | 仅性能问题按需采集，保留两类证据             |
| 网络配置与统计   | 明细可能较大，但对流量、网络类型定位有价值 | 仅网络问题按需采集，保留完整专项证据         |
| 存储空间与权限   | `df` 为小型容量摘要，包信息用于权限核对    | 保留                                         |
| 系统报告         | 整机级且无法按包名安全裁剪                 | 仅 ANR 默认选择，其他类型手动按需            |

## 已实施策略

1. 系统报告只在 ANR 默认勾选，因为线程和系统阻塞上下文对 ANR 定位有直接价值；其他问题类型改为手动按需选择，继续使用指定设备和两分钟硬超时。
2. 补采日志和实时日志先从目标包的 `dumpsys package` 读取 appId，再结合 Android 当前用户生成完整 UID。`logcat` 使用 `--uid=<uid>`；解析失败或设备不支持时终止该日志项，不回退全设备日志。
3. 普通“现存日志”只采集 main/system/events；“崩溃日志”单独采集 crash，消除两项之间的完全重复。
4. 设备环境快照改为精简白名单：时间、厂商、型号、Android 版本、API、构建指纹、ABI、系统语言/时区、屏幕尺寸/密度、内存摘要、磁盘余量、电量、目标包状态、字体缩放和应用语言。移除完整属性/设置、网络统计和 Wi-Fi 明细。
5. CPU、窗口、网络等专项证据只在对应问题类型默认出现。它们虽包含系统上下文，但对判断资源竞争、窗口状态和网络路径有实质价值，因此保留完整内容，不为压缩体积牺牲定位能力。
6. ZIP 和截图通过短期临时文件生成，形成最终附件后删除临时文件；成功 bugreport 删除原始输出目录。重新采集同一项目后，在草稿持久化成功后删除被替换的旧受管附件目录。
7. macOS ZIP 报告使用 Quick Look，避免系统归档工具自动解压。图片仍使用系统“预览”。

## 保留的边界

- `adb bugreport` 本身是整机报告，无法安全地按包名裁剪；ANR 保留默认采集，其他类型通过人工按需入口控制范围。
- 当前界面层级和截图仍可能包含屏幕可见信息；用户主动选择这些项目即表示需要保留当前画面证据。
- 网络、窗口和 CPU 专项仍可能包含系统上下文，但只在对应问题类型默认出现，且不会再被通用环境快照重复采集。
- 本轮不删除历史已存在的孤立文件，避免在缺少完整旧任务归属时误删用户附件；新的采集和替换不会继续制造同类重复。

## 验收要求

- 只有 ANR 的默认集合包含系统报告，其他问题类型不默认选择。
- 普通日志和崩溃日志命令包含目标 UID；普通日志不读取 crash buffer。
- UID 无法解析时不执行无过滤的 `logcat`。
- 环境快照包含小体积的内存摘要和磁盘余量，但不存在完整 settings、netstats 或 Wi-Fi dump。
- CPU、窗口和网络专项仍包含定位所需的系统上下文，并且只在对应问题类型默认选择。
- 成功系统报告只留下最终附件目录；中间 ZIP/截图文件不存在。
- 同一项目重新采集后，旧生成附件目录被删除，导入附件不受影响。
- macOS ZIP 预览不会调用默认归档解压流程。
