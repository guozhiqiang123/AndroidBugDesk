# AndroidBugDesk 小队协作约定

生效日期：2026-10-09。AndroidBugDesk 的真实版本父任务交给「AndroidBugDesk 交付小队」，由协调员拆分、派发、核对交付和推进阶段，成员承担实际开发、构建和独立验证。一个版本保留一个真实父任务；模板和路线图用于计划，不作为正在执行的版本。

## 角色与文件所有权

| 成员 | 负责工作 | 执行边界 |
| --- | --- | --- |
| AndroidBugDesk 协调员 · Codex | 需求澄清、拆任务、确定依赖、派发、验收技术成果、汇总 | 可只读理解代码和 Git；不直接写业务代码、修改资产、完整构建测试或合并分支 |
| 桌面后端开发 · Codex | Rust、ADB、证据、云效请求、凭据和持久恢复及专用测试 | 按子任务列明的文件范围执行，保留已有成果 |
| 桌面界面开发 · Codex | renderer、交互、中文界面、图标及界面专用检查 | 不自行修改 Rust 业务、共享 Schema 和锁文件 |
| 桌面构建与集成 · Codex | CI、共享契约和注册、锁文件、成果集成、候选构建与 Git 交付 | 是版本集成和候选分支的单一写入者；依照 Git 约定和当前授权操作 |
| 桌面验证与验收 · Codex | 独立审查、回归、验收证据 | 默认只读实现；发现问题交回实现成员，再审查新提交 |

这些角色是执行规范，不是操作系统级权限隔离。核对实际运行和交付，才能发现成员越界。用户已选择的模型、思考与速度设置保持原值；新增两个成员沿用原开发成员的配置。

## 从对话进入任务

仍在协调员对话提出需求。协调员集中补齐版本归属、目标、范围、验收和授权，再复用或建立版本父任务，负责人选择交付小队。仅要求讨论或规划时，任务保留 `backlog`；明确要求开始实施后才触发派发。

当前入口是「推进当前版本」「提出新需求」「查看进度与阻塞」。后者只查询，不启动工作。缺少版本时先让使用者选择，不能从最近任务或分支名称推定。

已知范围的独立 Bug 或小功能可以直接交给合适成员，也要有明确任务、文件范围、输入提交和验收。跨模块任务先交给小队，不能因为工作量小就由协调员自行实现。

## 并行和依赖

需求及接口契约确定后，后端、界面与独立 CI 配置可并行。一个版本默认最多三个成员执行任务；实际运行数还受本机可用名额限制。迁移时本机总并发上限为两个运行，此次保留该设置；队长派发后结束，释放名额供成员。工作未释放时排队，不把旧运行重复启动。

并行模块各用自己的 Multica worktree 和任务分支。共享契约、注册、配置、锁文件由集成者单一维护；其他成员提出变更请求。接口未准备好时，界面按约定 mock 推进，不自行接管后端。

集成等待实现成果被接受；独立技术验证等待集成提交；候选打包等待技术门槛；安装、USB、真实接口验收使用对应候选。最终主分支合并和本地同步按 `docs/git-delivery-policy.md` 执行，之后汇总。先推候选供打包，再验收，再合入主分支。

## 一次派发与回执

1. 队长读取真实版本、授权、当前提交和已有运行，选择能够开始的子任务。
2. 子任务分配给对应成员，状态登记使用 `--no-start`。在子任务内发一条正式成员提及评论，作为唯一启动信号；不再通过额外赋值、状态变更或 rerun 重复启动。
3. 小队父任务记录简短、不提及任何人的路由回执；队长记录 `squad activity` 决策，保持父任务进行中，然后结束本轮。
4. 成员在子任务触发评论线程交付，保留回复目标，并以 `/note` 开头，避免详细交付先唤醒一次队长。子任务设为 `in_review`，再给小队父任务一条普通、不提及任何人的简短交付回执，作为唯一评估信号。记录实际分支、提交、检查、产物和未覆盖项。
5. 队长收到回执后核对实际执行，接受技术成果、派返修、推进依赖或向人报告等待项。等待人工、输入或上游时写明 `waiting_on`，结束本轮。

正式提及会产生运行，不能用来致谢或签名。回复智能体评论也可能自动触发原智能体；因此子任务详细报告、感谢或确认使用 `/note`，小队父任务的唯一交付回执不使用 `/note`。任务链接只是引用，可用于回执。业务子任务尽量保留独立执行记录；若平台把成员运行绑定到父任务，必须明确目标子任务和范围，成员不能接管版本父任务状态。

## 现有成果与验收

迁移只改变分工，保留已经交付的分支、提交和状态。GZQ-45、GZQ-48 已完成，不因换组织而重开。GZQ-46 以最新恢复返修提交为准；GZQ-47 和图标沿用已有交付，人工界面验收按实际结果推进。新界面成员需接入指定旧成果，不从 `master` 旧界面重做，不占用旧成员的 worktree。

首版 GZQ-43、模板 GZQ-56、下一版本 GZQ-71 和路线图 GZQ-66 已改为小队负责。模板、下一版本和路线图继续停车，已有授权和人工验收保持。当前在途旧协调员审查继续完成交接；后续业务审查交给独立验证成员。

状态、运行结束、分支存在、取消任务、CI 成功各自只说明对应事实。整体验收仍需要实际证据，人工 UI、安装、USB 和真实云效写入不能用 mock 或智能体推断代替。原源码目录的静态实施记录可能早于任务交付，以最新任务 metadata、实际提交和当前人类指令核对。

目标任务已完成或取消时，晚到的阶段事件与回报只作备注并结束，不把任务改回进行中或审核中。只有用户明确重新开启或提出新实施要求时才继续执行。关闭任务不会自动中断已在运行的智能体，因此收尾须核对执行记录和最后回执。

Git 历史公开门槛待确认时，不推送源码。用户允许本地合并不代表允许公开历史。凭据、真实日志、设备隐私和证据包不进入源码库。

## 平台机制依据

小队任务先唤醒队长，队长按成员能力派发；小队不会自行启动所有成员。成员在小队任务中的无提及回执可唤醒队长；派发后队长应结束本轮。这些行为依据 [Multica 小队文档](https://multica.ai/docs/zh/squads)。

阶段完成事件只是推进提示，下一步仍需核对门槛。状态和阶段语义见 [任务文档](https://multica.ai/docs/zh/issues)。本项目本地目录继续使用并行 worktree，成果合并需要明确执行，见 [项目资源文档](https://multica.ai/docs/zh/project-resources)。

普通回复的自动路由与 `/note` 停止触发机制见 [评论中提及智能体](https://multica.ai/docs/zh/mentioning-agents)。本项目选用子任务备注加父任务单次回执，避免同一交付产生两轮队长评估。
