## 本机 macOS 打包

唯一常规入口：

```sh
npm run bundle:local
```

可指定新的产物目录：

```sh
npm run bundle:local -- --output artifacts/local-review-new
```

如果仅修正签名/包格式或流程脚本，业务源码和已编译产物没有变化，可复用本入口的已验证编译回执：

```sh
npm run bundle:local -- --from-build artifacts/previous-build --output artifacts/rebundled-new
```

复用模式会核对原回执的成功编译/验签/架构阶段、项目标识、源码、工具链及编译文件来源，不满足条件时要求重新编译。重新生成应用后再次验签，生成 DMG 时固定同时保留 app；全程没有 Rust build 阶段。回执分别记录实际编译和复用来源，不把复用写成一次新编译。

脚本只支持本机 macOS arm64/x64；校验 Node/Rust 架构一致，使用现有原生缓存。读取 `src-tauri/tauri.local-macos.conf.json` 的 ad hoc 签名 `-`，同时固定本机签名环境，避免继承发布证书/公证环境。此配置不自动合入跨平台/正式发布配置。

流程为：记录源码指纹 → 构建并签名 `.app` → 验证完整应用签名和架构 → 检查源码未变 → 生成带相同签名的 DMG → 校验 DMG、包内应用签名及文件一致性 → 再核对源码 → 写入成功回执。任何阶段失败立即停止，保留失败回执和日志，不能将旧包当成本轮产物。

每次使用新产物目录，保存 `.app`、`.dmg`、SHA-256、源码输入清单、各阶段日志和耗时、`bundle-receipt.json`。脚本不登录、不操作 USB、不安装。需要处理签名或包格式问题时，若已编译源码仍未变化，只重做 bundling；不要重新编译业务代码。对发布证书/公证的问题单独处理，不能用本机签名冒充发布签名。

这里的“新产物目录”必须尚不存在，入口自行创建目录。不要提前 `mkdir`，也不要将预检回执或重定向入口日志写到该目录；先写入独立预检目录或临时日志，入口创建产物目录后再补入对应记录。若目录保护拒绝执行，保留原记录并选择另一个尚不存在的输出目录，不能删除旧产物绕过保护。2026-10-10 曾因提前写入预检记录触发此检查，尚未开始编译；记录保留在 `artifacts/local-ui-refinements-macos-arm64-20261010/`。

本次复用编译完成的真实打包及全部签名/DMG/文件校验共 22.9 秒，其中 DMG 生成约 19.9 秒、完整性检查约 1.9 秒；没有重跑约两分钟的 Rust 发布编译。10 项流程测试与 69 个实际 React 模拟场景通过，四组界面检查使用独立端口，最长一组约 12.8 秒。这些时间来自回执，不代表未来机器上的固定耗时。成功产物及日志位于 `artifacts/local-workflow-proof-final-macos-20261009/`、`artifacts/workflow-retrospective-20261009/`。

## 检查与失败诊断

业务、共享结构或 Rust 改动运行完整 `npm run check`、Rust fmt/Clippy 和受影响界面流程。只有构建/检查脚本改动时运行 `npm run test:workflow`、受影响的实际流程及格式/差异检查；只有文档改动时不重跑业务测试。相同源码输入与工具链已经通过的检查可复用，输入变化、已知失败或新的疑点才触发对应重跑。

四个界面脚本共用 `browser-check-support.mjs`，通过 Vite API 启动独立动态端口，不再复制启动轮询。仍使用模拟 IPC 并阻止非本机请求。使用项目可用的 Playwright，或用 `PLAYWRIGHT_MODULE` 指向已安装模块；`CHROME_PATH` 可选择本机浏览器，`QA_OUTPUT` 指定独立输出目录。开始时清除旧成功状态，失败自动覆盖结果并保存最后至多三个页面的截图、HTML、URL 和错误堆栈；结束等待服务真正关闭，并记录耗时。

共享模块校验检查前后的 renderer、脚本和夹具指纹，拒绝将运行中变化的代码标为通过。它不通过延长超时、强制点击或自动多次重试掩盖失败。诊断截图属于模拟检查资料，不采集已安装客户端或真实令牌。

## 已授权的覆盖安装

2026-10-10 用户明确：当前是首版开发，安装新包直接覆盖，旧草稿丢失可以接受。此约定覆盖此前“先保存草稿、备份旧应用和本地数据”的安装要求。后续不检查、保存、迁移或恢复旧草稿，不因旧包/数据备份或回退准备延迟安装；备份按实际需要选择，不设为安装前置步骤。通常只替换应用目录，不主动清空本地数据，已有历史备份继续保留。

确认打包回执通过；旧应用正在运行时，重新取得原生绑定并直接正常退出，无需保存草稿。退出后只用只读进程检查，避免 AX/screenshot 自动重新拉起。将已验证应用覆盖到 `/Applications/Android Bug Desk.app`，重新绑定该路径启动，检查可见界面、运行进程路径、签名和安装文件一致性，记录安装结果。保留固定签名和包完整性校验，避免签名问题返工；不要把打包成功写成安装成功，也不要为了启动检查主动登录真实云效。

覆盖安装后首次原生绑定超时，先只读确认新应用进程是否已运行。如果进程存在，重置一次 `cua_repl` 再按安装路径绑定，不连续重复相同观察，也不因此重打包或重装。2026-10-10 的统一附件版连续两次绑定超时，重置连接后立即恢复，并确认新版界面；这个结果只能说明该次连接恢复有效，不能将所有启动超时都归为同一原因。

## 持久数据结构变更与启动冒烟

删除或重命名严格反序列化结构中的字段时，必须在存储恢复之前提供原子迁移，并用包含旧字段的真实形状夹具验证“打开旧数据库 → 迁移 → 严格反序列化 → 恢复”完整链路。不能只更新 Schema、模型和新建草稿；`Profile`、`Submission`、设置、选择记忆和嵌套快照都要纳入影响扫描。迁移应有单调递增的 SQLite `user_version`，重复启动不得重复破坏数据。

覆盖安装后的启动冒烟至少包括：记录启动前崩溃报告清单、从 `/Applications` 启动、等待进程持续存活、确认主窗口完成加载、核对关键新增控件，以及检查启动后没有新增 DiagnosticReports。仅看到瞬时 PID 或 `open` 返回成功不能写为启动成功。若发生崩溃，先保留该产物和原生日志，定位并修复根因，再使用新的产物目录重新完整打包；禁止把崩溃包或旧包写成最终安装结果。
