# 设备环境快照并发卡顿修复计划

## 问题与证据

2026-10-14 在 macOS 开启软件调试后执行“设备环境快照”，界面长期停留在“正在读取设备环境…”。本机运行日志、SQLite 状态和进程采样给出一致证据：

- 快照任务于 12:13:53 开始，17 条白名单 ADB 命令中的前 15 条在约 1 秒内完成；第 16、17 条未开始。
- 任务仍是 `pending`，环境采集项仍是 `running`，草稿没有生成附件。
- 12:14:24 起主线程看门狗每约 30 秒记录一次无响应。
- 进程采样显示主线程和一个 Tokio 工作线程都在等待 pthread mutex；没有遗留 ADB 子进程，进程 CPU 很低。
- 同一台设备在此前一分钟完成过同类快照，故障不符合 ADB 命令本身持续运行或设备传输拥塞的特征。

代码审查确认有三条并发路径共同访问同一个 SQLite 文件：

1. 快照任务在每条命令前重新校验草稿、账号、项目与包名绑定。
2. 新建提交页每 800 毫秒读取补采状态。
3. 前台页面观察每秒可能读取并更新当前草稿。

当前 `Store::connect` 在每次读写连接建立后都执行 `PRAGMA journal_mode=WAL`。日志阶段和进程采样表明，卡顿发生在一次命令完成后的绑定校验阶段。结论是连接级数据库初始化与高频并发读写发生锁竞争，并进一步阻塞了 macOS 主线程上的同步状态查询。

## 修复目标

- 普通数据库连接不再重复切换日志模式。
- 补采状态查询不阻塞 Tauri/macOS 主线程。
- 环境快照和补采执行期间暂停同一草稿的前台页面观察，完成或失败后按当前绑定安全恢复。
- 软件调试日志能够区分 ADB 命令、附件生成和持久化阶段，后续卡顿可以直接定位。
- 高并发状态读取、草稿更新和环境快照能够在限定时间内结束。

## 实施步骤

1. 在 `Store` 初始化数据库时一次性启用 WAL，并在进程内复用同一连接；短时数据库操作由连接互斥锁串行化，避免 macOS SQLite 文件层全局互斥锁在频繁开关连接时形成锁队列。
2. 将 `post_capture_status` 改为异步 Tauri 命令，保持前端调用契约不变。
3. 为 `AppState` 增加“仅停止指定草稿观察器”的操作。启动补采后暂停该草稿观察器，任务结束后仅在账号、项目、设备和包名绑定仍有效时恢复。
4. 在每个补采项加入操作阶段日志：当前命令序号/总数、生成附件、持久化和最终结果。日志不记录设备序列号、包名、命令输出或用户内容。
5. 增加回归测试，覆盖数据库并发读写，以及环境快照执行期间同时轮询状态和更新页面观察结果的场景。

## 验收条件

- 环境快照的固定 17 条命令均能执行到结束，任务不永久停留在 `pending/running`。
- 状态轮询与草稿更新并发运行时，测试在 5 秒内结束且生成环境快照附件。
- `Store` 不再为每次读取或写入重新打开数据库，也不再重复执行 `journal_mode=WAL`；初始化后的 journal mode 仍为 WAL。
- 前台页面观察在补采期间停止，任务结束后只为原草稿与原设备恢复；工作区或包名变化时不恢复。
- `npm run check`、Rust 格式检查、相关 Rust 测试和严格 Clippy 通过。

## 风险与回退

- 暂停观察期间不会更新可选的“Bug 所在页面”；快照结束后恢复，且不会覆盖人工填写值。
- 如果恢复观察时绑定已变化，保持停止状态并记录日志，避免写入错误草稿。
- WAL 初始化调整不改变表结构和数据格式；若回归测试发现兼容问题，可恢复初始化策略，但不得恢复每次连接切换 journal mode 的行为。

## 实施结果（2026-10-14）

已按本计划完成：

- `Store` 在启动时建立并配置单一 SQLite 连接，后续读写复用该连接；复合写入仍由原有写锁保护。
- `post_capture_status` 已改为异步 Tauri 命令，前端调用参数和返回值未变化。
- 同一草稿的前台页面观察器会在环境快照或补采开始时暂停，并在任务结束且绑定仍有效时恢复。
- 每个采集项记录命令进度、附件生成、持久化及结束结果，不保存命令输出或业务标识。
- 新增数据库并发、快照与状态/页面并发、观察器暂停恢复三类回归测试。

验证结果：`npm run check` 通过（前端类型、单元测试、生产构建、186 项 Rust 测试；3 项需真实设备/授权的测试按设计跳过）；补采专项 12 项通过、2 项真实设备测试跳过；严格 Clippy 通过；补采浏览器模拟通过。尚未在本机安装包中执行真实 USB 人工复测。
